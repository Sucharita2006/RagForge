# Phase 3 — Eval Harness + CI Gates

**Status:** complete
**Date:** 2026-08-02
**Spec reference:** `SPEC.md` §10 Phase 3
**Acceptance criteria:** a PR that worsens retrieval fails CI automatically.

## Goal

Turn the ad-hoc, mini-golden-set eval scripts from Phase 1/2 into a real harness: a curated ~120-item golden set (single-hop, multi-hop, unanswerable, adversarial), retrieval + generation + LLM-judge metrics with bootstrap 95% confidence intervals, persisted eval runs queryable from an Evaluations page, a formal `baselines/baseline.json`, and an automated CI gate that fails a PR on a real retrieval regression.

## What was built

- **Golden set v1** (`eval-datasets/v1/`): 117 curated items — 55 single-hop, 29 multi-hop, 23 unanswerable, 10 adversarial (target was ~120/55/30/25/10; see "What changed" below for why the unanswerable count landed at 23) — generated by sampling real corpus chunks and prompting the local model per item (`backend/scripts/generate_golden_set.py`), then deduplicated and curated (`backend/scripts/curate_golden_set.py`). Derived `calibration.jsonl` (40 items, weighted toward unanswerable/adversarial for Phase 4's abstain-threshold fitting) and `ci_split.jsonl` (30 items, a real subset of the golden set for fast local/manual retrieval-only checks).
- **Eval harness** (`app/evals/`): `retrieval_metrics.py` (hit_rate/MRR/NDCG@10, forbidden-string/abstention checks), `judge.py` (a single combined pointwise-rubric LLM call scoring faithfulness/answer_correctness/context_precision/context_recall in one round trip, Redis-cached by `(question_id, answer_hash, judge_model, prompt_version)` per implementation-plan.md C2), `bootstrap.py` (percentile bootstrap CI for a metric mean or a delta between two runs), `runner.py` (orchestrates retrieval for every item, generation+judge for a caller-specified subset, persists per-question `EvalResult` rows, aggregates into `EvalRun.metrics`).
- **Data model** (migration `0005`): `eval_datasets` (a registry row per golden-set version), `eval_runs` (one harness execution — name/config/dataset_version/status, plus an aggregate `metrics` column beyond SPEC.md's table, see "Key decisions"), `eval_results` (per-question drill-down: retrieved candidates, generated answer, computed metrics, judge rationale).
- **API**: `POST /api/eval/run` (enqueues a Celery task, returns immediately — a full pass is hours, not seconds), `GET /api/eval/runs`, `GET /api/eval/runs/{id}` (with per-question drill-down).
- **Evaluations page** (`frontend/app/evaluations/`): runs list with key metrics, metric cards with bootstrap CIs for the selected run, per-question drill-down table.
- **`baselines/baseline.json`**: formalized on golden-set v1 (retrieval metrics on all 117 items; faithfulness/answer_correctness/context_precision/context_recall/abstention on a stratified 39-item subset — see "Key decisions" for why not all 117).
- **CI** (`.github/workflows/evals.yml`): a real, automatic, per-PR retrieval regression gate against a tiny synthetic fixture corpus (`backend/scripts/generate_ci_fixtures.py`) — ingests fresh, queries end-to-end, hard-fails if any answerable fixture question doesn't retrieve its correct document at rank 1. Deliberately *not* the real golden-set-v1 + baseline.json regression rule; see "Key decisions."
- **Tests**: `test_eval_retrieval_metrics.py`, `test_eval_bootstrap.py`, `test_eval_judge.py`, `test_golden_set_generation.py` — 26 new unit tests, two of which caught real bugs before they shipped (see "What changed").

## What changed from the original design (and why)

Full rationale in `DECISIONS.md`; summary of what surfaced only once this ran for real:

1. **Self-hosted-only for golden-set generation and judging, by explicit choice.** The kickoff plan called for a free Gemini key powering exactly these two jobs (the local 4B model's weakest spots per the original provider-layer decision). Asked directly rather than assuming; the answer was to stay fully self-hosted for now. `JudgeProvider` takes its `LLMProvider` as a constructor argument, so swapping in a Gemini-backed judge later needs no harness changes.
2. **`GEN_TEMPERATURE=0.1` collapsed "unanswerable" question diversity.** 17 of the first 25 generated unanswerable items were near-duplicates of one topic (a shuffled corpus-title list alone wasn't enough perturbation to escape the model's single strongest low-temperature completion). Fixed with Jaccard word-overlap deduplication plus a backfill pass that explicitly lists every already-used topic to avoid — a directive constraint the model reliably honors even at the same low temperature. Landed at 23 final unanswerable items (2 residual near-duplicates from the backfill batch itself were caught by a second dedup pass and not replaced, rather than spending another generation round chasing an exact 25).
3. **A reference-list chunk nearly became a "single-hop" golden item.** The corpus-chunk sampler picked a bibliography block, and the model wrote a plausible-sounding question about *a citation's title* rather than the paper's own content. Fixed with a heuristic pre-filter (`_looks_like_references`).
4. **A real serialization bug caught by writing the harness's own tests, not manual testing**: `EvalRunOut`/`EvalResultOut` were missing `from_attributes=True`, so returning raw ORM objects from the API (the established pattern elsewhere in this codebase) would have failed at request time — caught by comparing against `schemas/documents.py`'s pattern while reviewing the new endpoints, before ever making a live request.
5. **The judge regex didn't handle negative scores** (`ANSWER_CORRECTNESS: -0.2` failed to parse at all instead of clamping to 0.0) — caught by a unit test that deliberately fed an out-of-range value, not by eyeballing the parser.
6. **`evals.yml` cannot literally run SPEC.md §8.3's "30-item CI subset of the real golden set"** on a free GitHub-hosted runner — there's no persistent volume or hours of Docling/embedding time to rebuild the real 40-document corpus on every PR, and no feasible way to host Ollama warm and fast in a stock runner. The real `ci_split.jsonl` (a genuine golden-set-v1 subset) exists for local/manual fast checks; the actual automated CI gate uses a separate, clearly-labeled tiny fixture corpus instead — a real, working, automatic gate, just a narrower one than the spec's original wording implies. See `DECISIONS.md` for the full reasoning.
7. **The hand-rolled CI fixture PDFs sometimes trigger Docling's OCR path.** No PDF-writing dependency was added just to produce 4 tiny files — a minimal valid PDF is easy to construct by hand — but an unusual-enough PDF structure occasionally reads as "scanned" to Docling's layout model. Confirmed live (3 of 4 fixtures fell back to pypdf). `DOCLING_TIMEOUT_SECONDS=10` in the CI job keeps this fast; Phase 2's timeout-guard fix makes the parser choice irrelevant to correctness either way.

## Key decisions this phase

- **One combined judge call instead of four** (faithfulness/answer_correctness/context_precision/context_recall in a single pointwise-rubric prompt) — the same plain-prompt-over-many-small-calls lesson as Phase 1's generation-prompt finding, and a direct latency win on CPU-bound local inference.
- **`eval_runs.metrics` as an aggregate column**, beyond SPEC.md §5's literal table — avoids recomputing bootstrap CIs from every `eval_results` row on each Evaluations-page load.
- **Full generation+judge pass runs on a documented subset (39/117 items), not everything** — measured single-item full-pipeline latency (main generation + judge call) runs 150–450s on this 8GB CPU-only local profile; a full ~120-item pass would take 8–12+ hours for one baseline. Retrieval metrics still run on the complete golden set (cheap, no generation needed).
- **The CI gate is a fixture-corpus smoke test, not the spec's literal real-corpus CI subset** — disclosed and reasoned through above, matching this project's established practice of scoping around free-tier CI/hardware constraints rather than silently pretending full coverage.
