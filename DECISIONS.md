# DECISIONS.md

Deviations from `SPEC.md`, recorded as they're made, per SPEC.md §0.3: "If a library choice in this spec fails/conflicts, prefer the simplest working alternative and record the decision here." Full rationale for each lives in `document/implementation-plan.md`; this file is the terse changelog.

---

## 2026-07-30 — Provider layer: self-hosted-first, not Gemini-only

**Spec said:** Gemini 2.5 Flash/Pro for generation, judging, and enrichment; `gemini-embedding-001` for embeddings (§2, §9).
**Decision:** `LLMProvider`/`EmbeddingProvider`/`RerankerProvider` interfaces speak an OpenAI-compatible API. Default generation = **Qwen3-4B-Instruct via Ollama** (runs natively on the Windows host, not in Docker, to keep model RAM off the WSL2 cap). Default embeddings = **`BAAI/bge-small-en-v1.5`, 384-dim**. Default reranker = **`cross-encoder/ms-marco-MiniLM-L-6-v2`**. A free (no-card) Google AI Studio key is used *only* for LLM-as-judge, golden-testset generation, and contextual enrichment — capped by a hard budget guard — since a 4B local model is weakest at those three offline, quality-critical jobs. Gemini remains available as a swappable provider for anyone who wants to run the full spec as written.
**Reason:** user cost constraint — paid LLM APIs for every generation call were ruled out.

## 2026-07-30 — Cloud budget: $0/month free-tier stack

**Spec said:** Cloud SQL (Postgres), GCS, Secret Manager, Cloud Run (§1.3, §2).
**Decision:** Cloud Run (scale-to-zero) + a free-tier Postgres with pgvector (Neon or Supabase) + a free-tier Redis (Upstash) for the ongoing public demo. GCS/Secret Manager usage kept inside free tiers or substituted.
**Reason:** user chose the $0/month option over paid GCP or trial credits.

## 2026-07-30 — Demo corpus: arXiv LLM/RAG papers

**Decision:** seed corpus is 30–50 arXiv papers on LLMs/RAG (not spec's generic "seed demo corpus").
**Reason:** recognizable to technical reviewers, stresses Docling (two-column layout, tables, math), freely redistributable.

## 2026-07-30 — 8GB-RAM/CPU-only local profile

**Decision:** all local-inference models sized for CPU on 8GB RAM (see `document/implementation-plan.md` §3): 4B-class quantized generator, 33M embedder, 23M reranker, RoBERTa-size NLI (MiniCheck). Ollama runs natively on Windows, not inside Docker. `docker-compose.yml` sets explicit `shm_size` on the postgres service.
**Reason:** user's available hardware.

## 2026-07-30 — Phase-2 exit gate fixed (spec circularity)

**Spec said:** Phase 2 exit = "NDCG@10 beats baseline-v0 on `ci_split`" (§10), but `ci_split.jsonl` and the eval harness don't exist until Phase 3 (§10 Phase 3).
**Decision:** Phase 1 ships a small hand-curated mini golden set (~20 items) + a deterministic `scripts/run_eval.py` (hit_rate@k, MRR, NDCG@10, no LLM judge) so `baseline-v0` has real numbers from day one and Phase 2 has something concrete to beat. Phase 3 formalizes into the full golden set + judge.

## 2026-07-30 — Streaming vs. structured generation output split

**Spec said:** structured JSON output (`answer_sentences[]` with citations) *and* an SSE streaming variant (§3.3) — these conflict; you can't stream prose and return strict JSON from the same call.
**Decision:** `POST /query` = non-streaming structured JSON. `POST /query/stream` = streams prose with inline citation markers (`[c12]`), parses sentences+citations at end-of-stream, runs claim verification, emits the trust payload as a terminal SSE event.

## 2026-07-30 — Golden dataset resized

**Spec said:** 200 full / 60 calibration / 50 CI-subset items (§8.3).
**Decision:** ~120 full (55 single-hop, 30 multi-hop, 25 unanswerable, 10 adversarial) / 40 calibration / 30 CI-subset.
**Reason:** keeps judge runtime and free-tier LLM-judge quota feasible on the self-hosted/hybrid setup while remaining statistically meaningful.

## 2026-07-30 — CI gates split into hard/soft

**Spec said:** all Section 7.2 metrics gate CI (§8.7).
**Decision:** deterministic retrieval metrics (hit_rate, NDCG, etc.) hard-fail CI; LLM-judge metrics (faithfulness, answer_correctness) soft-fail/warn or use a 2-run median.
**Reason:** LLM-judge scores are noisy enough that hard-gating on them would fail PRs randomly.

## 2026-07-30 — Latency & filtering architecture (research-informed)

**Trigger:** a claim that pgvector metadata pre-filtering beats post-filtering (12ms/45ms/18ms-style numbers) for vector search at scale. Dedicated research (`document/research-latency-optimization.md`) found the specific numbers unsourced but the underlying pgvector failure mode real and documented in pgvector's own README.
**Decision:**
- `hnsw.iterative_scan = relaxed_order` set as default for filtered queries (pgvector ≥0.8.0); partial HNSW indexes added for known low-cardinality metadata filters; pgvector pinned **≥0.8.2** (buffer-overflow CVE fix).
- `halfvec` (fp16) storage adopted for the embedding column.
- A **multi-architecture sweep** (filtering strategy × quantization × `ef_search` × concurrency) is run on our own data/hardware rather than assuming any single source's recommended config — see `document/implementation-plan.md` §2.E4.
- A large-scale synthetic benchmark (separate from the small real demo corpus) uses a real public embedding dataset (`abokbot/wikipedia-embedding`, 384-dim, dimension-matched to our own embedder) with our own chunks unioned in as "needle" vectors — not random synthetic vectors.
- **Capped at ~250K–500K vectors, built locally, $0** — a full 1M-vector HNSW index needs ~10–25GB RAM with graph overhead, not feasible on the 8GB local machine; no cloud VM spend was approved for this.
**Reason:** user wants a defensible, reproducible "least latency, solid numbers" resume claim; research showed no single filtering approach wins at every selectivity, so the honest approach is to measure and report the sweep, not assert one config.

## 2026-07-30 — Frontend: Next.js 16.2.12 / React 19, and a flat-config fix

**Spec said:** Next.js 14+ (§2).
**Decision:** scaffolded with **Next.js 16.2.12 / React 19** instead (14 predates current stable by several majors; spec's "14+" already permits this). During Phase 0 verification, `eslint.config.mjs` built with the documented `FlatCompat` + `compat.extends("next/core-web-vitals", "next/typescript")` pattern crashed (`TypeError: Converting circular structure to JSON` inside `@eslint/eslintrc`) — `eslint-config-next@16.2.12` no longer exports legacy named configs for that bridge; it exports a flat-config array directly (`export = config: Linter.Config[]`). Fixed by importing it directly: `import nextConfig from "eslint-config-next"; export default [...nextConfig]`. `@eslint/eslintrc` dependency removed as unnecessary.
**Reason:** ecosystem has moved past the FlatCompat pattern still shown in some older tutorials; discovered by actually running `npm run lint` during Phase 0 verification rather than assuming the scaffold worked.

## 2026-07-30 — Known, accepted dev-tooling vulnerabilities (non-blocking)

`npm audit` reports 12 high-severity findings on the frontend, all in build-time/lint tooling, not runtime code we control:
- `postcss`/`sharp` vendored **inside Next.js 16.2.12 itself** (`next/node_modules/...`) — already latest stable; no newer release fixes this yet.
- `eslint-plugin-react`/`-import`/`-jsx-a11y` (via `eslint-config-next`) pull an old `minimatch`/`brace-expansion` — fixing requires an eslint 10 major bump that `eslint-config-next` doesn't yet declare support for.
**Decision:** accepted for now; re-check each phase close (`npm audit`) and bump when upstream catches up. Not forcing `npm audit fix --force`, which would downgrade `next` to `9.3.3` or `eslint` to a version `eslint-config-next` doesn't officially support — either would break more than it fixes.
**Reason:** these are dev-time supply-chain findings with no exposure through the deployed app's runtime attack surface; forcing fixes now would trade a cosmetic audit score for real breakage.

## 2026-07-31 — Generation: plain prose + parsed citations, not JSON-schema-constrained output

**Spec said:** structured output via a JSON schema (§3.3): `{"answer_sentences": [...], "insufficient_context": bool}`.
**Decision:** drop Ollama's `format` (JSON-schema-constrained/grammar) decoding entirely; the model generates plain prose with inline `[chunk_id=<id>]` citation markers, parsed into the same `GeneratedAnswer`/`ClaimOut` shape by `app/generation/parser.py`. `LLMProvider.generate_json(...)` became `LLMProvider.generate(...) -> LLMResult(text=...)`.
**Reason:** empirically, under grammar-constrained decoding our 4B local model (`qwen3:4b-instruct`) reliably took the trivial shortcut the schema didn't forbid — an empty `answer_sentences` array + `insufficient_context: true` — on a question the retrieved context clearly answered. The *identical* prompt/context with unconstrained plain-text generation answered correctly, cited correctly (in the exact `[chunk_id=...]` format asked for), and ran roughly 6x faster (~30-38s vs 235s+/timeout). This also collapses the earlier planned split between `POST /query` (structured) and `POST /query/stream` (prose + parsed markers, amendment A2) into one shared generation approach.
**Also fixed along the way (kept, though superseded as the primary fix):** Ollama defaults to a 4096-token context window regardless of what the model supports — added `OLLAMA_NUM_CTX` (default 8192) and `GEN_TIMEOUT_SECONDS` (default 300, later 600 — CPU inference of a large context is genuinely slow and varies run to run) to `config.py`.

## 2026-07-31 — Backend Docker build/runtime fixes (Phase 1 dependency additions)

Three build/runtime issues surfaced adding docling/sentence-transformers/torch for Phase 1, none in SPEC.md scope but each needed a real fix:

- **CPU-only torch wheel, not PyPI's default.** `pip install torch` pulls a ~530MB CUDA-bundled wheel that repeatedly stalled mid-download through Docker Desktop's network layer on this machine (reproduced twice). Fixed by installing `torch torchvision` together from `https://download.pytorch.org/whl/cpu` *before* the main `pip install -e ".[dev]"` step (torchvision pinned alongside torch, not separately, after installing torch alone first caused a version-mismatched `torchvision::nms does not exist` RuntimeError). Also just correct for our CPU-only profile — no CUDA runtime we'll ever use.
- **`libxcb1` and friends for Docling's table-structure model.** Docling's `docling_ibm_models` table-former model imports `cv2` (opencv), which needs `libgl1 libglib2.0-0 libxcb1 libxext6 libsm6 libxrender1` — absent from `python:3.12-slim`. Without them Docling's table model fails to initialize and the ingestion pipeline silently falls back to pypdf (still works, just loses Docling's layout/table fidelity, the whole reason arXiv two-column PDFs were chosen as the demo corpus). Added to the Dockerfile's `apt-get install` line; confirmed via a real re-ingest that `parser` flips from `pypdf` to `docling`.
- **Celery per-task event loop vs. a shared async engine pool.** `ingest_document_task` wraps each call in its own `asyncio.run()` (a fresh event loop every task), but `app/db/session.py`'s async engine/connection pool is a module-level singleton created once at worker startup. asyncpg connections are tied to the loop they were created on, so a pooled connection from task N's (now-closed) loop reused in task N+1 raised `RuntimeError: ... attached to a different loop`. Fixed by calling `await engine.dispose()` in a `finally` block after each task, forcing the next task to open fresh connections on its own loop. Caught mid-seed-run (6/13 documents had failed with this error); fixed, then a clean re-run ingested 36/40 papers with zero recurrences, the remaining 4 finishing shortly after their client-side polling timeout (a script issue, not a task failure — the worker had already completed them).

## 2026-07-31 — Citation parser: reattach trailing citations across a sentence-punctuation boundary

**Found via unit tests** (`backend/tests/unit/test_parser.py`), not manual testing: a naive sentence splitter (`re.split(r"(?<=[.!?])\s+", text)`) breaks when the model places a citation marker *after* a sentence's punctuation with a space in between (e.g. `"Both sources agree. [chunk_id=chunk-a][chunk_id=chunk-b]"`) — the split fires at the first `". "`, orphaning the citation-only fragment into its own "sentence" with no real text, which then gets silently dropped (`if clean_text:` guard). Fixed by using a capturing group in the split pattern (`(?<=[.!?])((?:\s*\[chunk_id=[^\]]+\])*)(?:\s+|$)`) so `re.split` interleaves the captured trailing-citation text back into the output list, then reassembling each sentence with the citation blob that followed it. The `(?:\s+|$)` alternation (not just `\s+`) matters too — without allowing end-of-string as a valid terminator, Python's greedy-then-backtrack regex engine backs off to matching zero citations just to satisfy a trailing whitespace requirement that can't be met at the end of the text.
**Reason this matters:** exactly the kind of thing that "looks like it works" in a couple of manual spot-checks (both real end-to-end tests happened to hit the case this bug didn't break) but silently drops citations in a systematic, reproducible way for a specific — and plausible — model output pattern. Real unit tests over the deterministic parsing logic caught it; manual testing alone had not.

## 2026-08-01 — `tsv` GENERATED ALWAYS column needs `Computed()` in the ORM model, not just the migration

**Found mid-reindex** (1/40 documents failed): the migration adds `chunks.tsv` as `GENERATED ALWAYS AS (to_tsvector('english', content)) STORED`, but the SQLAlchemy `Chunk` model declared it as a plain `mapped_column(TSVECTOR, nullable=True)`. SQLAlchemy doesn't know the column is DB-computed, so on some code paths it included an explicit `tsv=NULL` in the INSERT — Postgres rejects any explicit value (even NULL) for a `GENERATED ALWAYS` column: `cannot insert a non-DEFAULT value into column "tsv"`.
**Fix:** `mapped_column(TSVECTOR, Computed("to_tsvector('english', content)", persisted=True), nullable=True)` — `Computed()` tells the ORM to never include the column in INSERT/UPDATE at all.

## 2026-08-01 — halfvec migration must land before the model changes, not after

**Self-inflicted sequencing bug:** edited `Chunk.embedding` to `HALFVEC(384)` before running migration `0004_halfvec_migration` (which converts the actual `embedding` column from `vector(384)` to `halfvec(384)` and rebuilds the HNSW index with `halfvec_cosine_ops`). Caught by checking `alembic_version` (still `0003`) against the model's already-`HALFVEC` declared type before any data corruption occurred — stopped the in-progress reindex, ran migration 0004, restarted the worker, redid the reindex clean.
**Lesson:** when a migration changes a column's storage type, run and verify it *before* touching the ORM model, not alongside it — the two must never be out of sync even briefly during a live reindex.

## 2026-08-01 — Docling/RapidOCR has no internal timeout; a thread-based wall-clock guard isn't enough either

**Found on real data, twice:** one corpus document (`2410.12311v4`) drove Docling's automatic RapidOCR fallback for 5+ hours with no completion (confirmed genuinely computing via `docker stats`, ~380% CPU, not deadlocked) — Docling has no internal timeout for OCR.
**First fix:** wrap the parse in `concurrent.futures.ThreadPoolExecutor(max_workers=1)` + `future.result(timeout=DOCLING_TIMEOUT_SECONDS)`, falling back to pypdf on `TimeoutError`. This unblocked the pipeline correctly — but Python cannot forcibly kill a thread, so the abandoned OCR work kept running in the background indefinitely.
**Found live, independently, later in the same phase:** after a Docker Desktop restart and worker recovery, `docker stats` showed the worker container pinned at ~900% CPU with an *empty* Celery queue — the orphaned thread from an earlier timeout was still burning CPU forever, invisible to Celery (which had already moved on) and invisible to `celery inspect active` (which only sees task-level state, not the runaway thread inside a completed task).
**Real fix:** replaced the thread with a genuine child OS process (`multiprocessing.Process` + a result `Queue`, `process.join(timeout=...)`, `process.kill()` on timeout). A process can be SIGKILLed and its CPU actually reclaimed by the OS; a thread cannot. Verified live: worker CPU dropped from ~380–800% to 0.07% in the same instant the timeout fired and the pypdf fallback completed, and `docker compose logs worker` showed the OCR attempt running under a distinct `Process-1` name, killed cleanly at the 300s mark.
**Reason this matters:** the first fix looked complete (pipeline unblocked, task "succeeded", fallback worked) and shipped with an honest comment about the tradeoff — but "the task moved on" and "the resources were reclaimed" are different guarantees, and only load-bearing production behavior (CPU pinned at 900% with nothing queued) surfaced the gap between them.

## 2026-08-01 — pgvector's documented filtered-search bug doesn't reproduce on the real corpus at its actual size — and why that's the correct planner behavior

**Investigated for the Phase 2 exit criterion** ("a recall@k/latency curve reproduces then fixes pgvector's documented filtered-search failure mode, measured on the real corpus"). Running the sweep script as originally written (`backend/scripts/benchmark_filtering.py`) against a real per-document filter (2.0% selectivity, 30/1532 chunks) returned the full requested `top_k=10` at every `ef_search`/`hnsw.iterative_scan` combination — no bug, no curve.
**Root cause, confirmed via `EXPLAIN ANALYZE`:** at ~1.5K chunks, Postgres's own cost-based planner never chooses the HNSW index for this query shape at all — it picks a `Bitmap Heap Scan` on the `document_id` B-tree index (or, with bitmap/seq scan disabled, a plain `Index Scan` on the same B-tree, or with that index also gone, a full `Seq Scan`) followed by an *exact* sort, because at this table size any exact path is cheaper than the approximate ANN index. The bug is real but structurally unreachable below some corpus-size threshold — the planner sidesteps it correctly, on its own, without any GUC involved.
**To still exercise and fix the documented bug on real data:** the benchmark script now drops the competing `ix_chunks_document_id` index and sets `enable_seqscan = off`, both scoped to a transaction it always rolls back (never committed — restored even on a crash), forcing the planner onto `Index Scan using ix_chunks_embedding_hnsw`. This reproduces the bug cleanly: with `hnsw.iterative_scan = off`, **0 of the requested 10 rows** come back at every `ef_search` value tested (10/40/80/160) — the 30 chunks belonging to the filtered document simply aren't among the HNSW graph-traversal candidates. Switching to `iterative_scan = relaxed_order` fixes it to a reliable **10/10** at every `ef_search` value, at a measured ~3–4x latency cost (≈1–2ms → ≈4–6ms) — cheap insurance against silently incomplete results.
**Decision:** ship both halves of the finding — the "natural" plan (proof the bug doesn't threaten this corpus today) and the "forced" plan (proof it will threaten a larger one, and that the fix works) — rather than reporting only whichever one made the exit criterion easier to claim. `hnsw.iterative_scan = relaxed_order` stays the default per the 2026-07-30 filtering-architecture decision; this is corroborating evidence at real-corpus scale, not new fallout from it.

## 2026-08-01 — Phase 3 golden-set generation and judging stay self-hosted-only for now

**Spec/kickoff said:** a free Google AI Studio (Gemini) key powers golden-testset generation and LLM-as-judge scoring, since the 4B local model is spec-identified as weakest at exactly those two offline jobs (2026-07-30 provider-layer decision).
**Decision:** asked the user directly rather than silently defaulting; chose to proceed fully self-hosted (`qwen3:4b-instruct` via Ollama for both testset generation and judging) rather than set up a Gemini key right now. `JUDGE_PROVIDER=ollama` was already the config default, so no code change was needed — only the golden-set-generation script, which is new this phase.
**Consequence:** judge scores (faithfulness, answer_correctness, context_precision/recall) and generated golden-set questions reflect the weaker local model's judgment/creativity, not Gemini's. The `JudgeProvider`/generation-script LLM dependency is injected, not hardcoded, so swapping in a Gemini-backed provider later needs no harness changes — only a re-run.

## 2026-08-01 — Golden-set generation: two real data-quality bugs, found by inspecting output before trusting it

Both found by spot-checking generated items rather than assuming a "looks like it ran fine" script output was good data — same lesson as the citation-parser and tsv findings earlier in this project.

1. **Reference-list chunks make bad single/multi-hop source material.** The corpus-chunk sampler (`token_count >= 150`) happily selected a bibliography chunk (a block of citation entries), and the model dutifully wrote a plausible-sounding question about *a citation's title* rather than the paper's own argument — technically "answerable" but not a meaningful RAG eval item. Fixed with a heuristic filter (`_looks_like_references`: 2+ URLs, or 4+ `Lastname, X.`-pattern author-list matches) applied before a chunk is offered to the generator, with oversampling + retry so the target count is still reached.
2. **`GEN_TEMPERATURE=0.1` (the app-wide generation default, reused as-is by the golden-set generator) collapsed "unanswerable" question diversity.** Of 25 generated unanswerable items, 17 were near-duplicates of one topic ("IoT sensor data integration") — a shuffled corpus-title list alone wasn't enough perturbation to escape the model's single strongest low-temperature completion for "plausible but out-of-corpus RAG question." Caught by word-overlap (Jaccard ≥0.55) deduplication during curation (`scripts/curate_golden_set.py`), which dropped the duplicates and backfilled the shortfall one item at a time, each call explicitly listing every already-used topic to avoid — a directive constraint the model reliably honors even at the same low temperature, unlike passive shuffling.

## 2026-08-01 — Phase 3 eval-harness schema: `eval_runs.metrics` added beyond SPEC.md §5's table

**Spec said:** `eval_runs` = `id, dataset_version, config jsonb, git_sha, started/finished, status` — no aggregate-metrics column; `eval_results.metrics jsonb` holds per-question metrics.
**Decision:** added `eval_runs.metrics jsonb` (nullable, populated on completion) as a run-level aggregate (bootstrap mean/CI per metric, `app/evals/bootstrap.py`), so the Evaluations page's runs list and CI regression checks don't need to re-aggregate every `eval_results` row on each load.
**Reason:** small, additive, backward-compatible with the spec'd shape; avoids an O(n) recomputation for a value that's cheap to compute once at the end of a run and never changes after.

## 2026-08-01 — Full generation+judge pass runs on a documented subset, not all ~120 golden-set items

**Spec implied:** every golden-set item gets full metrics (retrieval + generation + judge).
**Decision:** `POST /api/eval/run` always computes retrieval metrics (hit_rate/MRR/NDCG@10) for the full golden set — cheap, no generation needed. Generation+judge metrics (faithfulness, answer_correctness, context_precision/recall, abstention) run on a `full_pipeline_ids` subset the caller specifies; the harness itself imposes no cap. For `baselines/baseline.json`'s Phase 3 baseline, that subset is every 3rd item of the shuffled `eval-datasets/v1/full.jsonl` (~40 items, stratified by construction since the file is pre-shuffled across types).
**Reason:** measured single-item full-pipeline latency (main generation + judge call) at roughly 150–450s on this 8GB CPU-only local profile (implementation-plan.md B4); a full ~120-item pass would run 8–12+ hours for one baseline. ~40 items is enough for a bootstrap CI with a meaningful sample while keeping one baseline run to a few hours — consistent with this project's established practice of disclosing hardware-driven scope tradeoffs rather than silently running a smaller "full" set.

## 2026-08-01 — `evals.yml` CI gate: a fixture-corpus smoke test, not literally SPEC.md §8.3's "30-item CI subset"

**Spec said:** `evals.yml` runs eval on `ci_split.jsonl` (a 30-item subset of the real golden set) per PR, full set nightly, gated per Section 7.2's regression rules.
**Decision:** a real `eval-datasets/v1/ci_split.jsonl` (30 items, a real subset of the curated golden set v1) exists and is meant for fast local/manual retrieval-only checks against the real corpus — but the actual GitHub Actions `evals.yml` workflow uses a separate, clearly-labeled tiny synthetic fixture corpus (`scripts/generate_ci_fixtures.py`: 4 one-topic hand-rolled PDFs + `eval-datasets/ci-fixture/golden.jsonl`, 5 items) that it ingests fresh and queries end-to-end on every PR, hard-failing if any answerable fixture question doesn't retrieve its one obviously-correct document at rank 1.
**Reason:** the real golden-set-v1 needs the real 40-document corpus already ingested, embedded, and HNSW-indexed — rebuilding that from scratch on a free GitHub-hosted runner on every PR is not feasible (Docling/embedding time, no persistent volume). No LLM/judge runs in this CI job either, for the same reason Ollama isn't installable-and-warm cheaply in a stock runner. This *is* a real, working, automatic regression gate — a genuinely broken retrieval pipeline fails it — but it cannot catch subtler quality regressions the way a full `POST /api/eval/run` against the real corpus would; that stays a manual/local check against the persistent dev stack for now.
**Also found while building this:** the hand-rolled fixture PDFs (no PDF-writing dependency was added just for 4 tiny files — see the generator's own docstring) sometimes read as "scanned" to Docling's layout model and fall into its OCR path, confirmed live (3 of 4 fixtures fell back to pypdf, 1 succeeded via Docling). `DOCLING_TIMEOUT_SECONDS=10` in the CI job keeps this fast — the always-correct pypdf fallback (Phase 2's timeout-guard work) makes the parser choice irrelevant to correctness either way.

## 2026-08-02 — Eval runner: per-item failure isolation, and a longer generation timeout for background runs

**Found running the actual Phase 3 baseline eval**, twice: the first attempt died after ~10 minutes with `run.status="failed"` and an *empty* error message — `except Exception as e: run.error = str(e)` stored nothing useful because the exception itself (in this case) had no informative `str()`. Fixed the diagnosis gap first (`logger.exception(...)` + `traceback.format_exc()` in the stored error), then re-ran to get a real answer: `httpx.ReadTimeout` inside `OllamaProvider.generate()` — a multi-hop item's larger assembled context (two source excerpts, expanded to parents) pushed generation past `GEN_TIMEOUT_SECONDS=600`, the live-query default.
**Two separate fixes, both real:**
1. `OllamaProvider.__init__` now takes an optional `timeout` override (defaults to the existing `settings.GEN_TIMEOUT_SECONDS` when omitted, so the live `/api/query` path is unchanged). The eval Celery task constructs it with `timeout=1200.0` — eval runs are background/non-interactive and can afford to wait much longer than an interactive request ever should.
2. **The bigger fix**: `execute_eval_run`'s per-item loop wasn't isolated — one item's exception aborted the whole run, discarding every already-committed `EvalResult` from ever being aggregated (the rows survived in the DB, since each item commits individually, but `run.metrics` never got computed and the run showed `status="failed"` with zero visible signal). Moved the try/except inside the loop: a failing item is logged, rolled back, and recorded in a `failures` list; the run still completes and aggregates from whatever succeeded, only falling back to `status="failed"` if *every* item failed. `run.error` on an otherwise-`completed` run now doubles as a non-fatal "N/M items failed: [...]" advisory.
**Reason this matters:** a harness that can't tolerate one slow or genuinely-timed-out item among ~40 is too fragile to trust for a real baseline number — the whole point of computing a bootstrap CI over many items is that a handful of outliers shouldn't invalidate the run.

## 2026-08-02 — GitHub Actions CI never got the CPU-only-torch fix; both `ci.yml` and `evals.yml` were pulling ~1.5GB of unneeded CUDA wheels

**Found live**, once these workflows actually ran end-to-end against real GitHub-hosted infra after the Phase 3 push (both `ci / backend-lint-test` and `evals / retrieval-smoke-gate` failed): `backend/Dockerfile` was fixed back on 2026-07-31 to install `torch`/`torchvision` from `https://download.pytorch.org/whl/cpu` *before* `pip install -e ".[dev]"`, specifically because a plain install resolves the PyPI-default CUDA-bundled torch wheel — but that fix only ever touched the Dockerfile. Both `.github/workflows/ci.yml`'s `backend-lint-test` job and `evals.yml`'s `retrieval-smoke-gate` job still ran a bare `pip install -e ".[dev]"`, independently hitting the same problem the Dockerfile fix was written for.
**Confirmed by reproducing locally** in a clean `python:3.12-slim` container (no CPU-torch override): pip resolved `torch-2.13.0` plus `cuda_toolkit`, `nvidia_cudnn_cu13` (366MB), `nvidia_cusparselt_cu13` (170MB), `nvidia_nccl_cu13` (206MB), `nvidia_nvshmem_cu13` (60MB), `triton` (197MB), and `nvidia_cublas` (423MB) — over 1.5GB of GPU runtime libraries a CPU-only lint/test/ingestion job will never use — and the download of just one of those wheels hit a read timeout partway through, the exact same failure mode `DECISIONS.md`'s 2026-07-31 entry already documented for Docker Desktop's network layer.

## 2026-08-03 — Real calibration run: the abstain threshold landed at 0.01, and why that's a real result, not a bug

**Ran `scripts/calibrate_abstain_threshold.py` for real** against all 40 `calibration.jsonl` items (full retrieve→generate→verify pipeline each). Result: **chosen threshold 0.010** (swept range [0,1], target ≥90% answered-precision) — a much lower, more permissive number than the `config.py` bootstrapping default of 0.55.
**Why, confirmed by reading the raw per-item scores, not just the final number:** every one of the 23 genuinely-unanswerable items scored `confidence=0.000` exactly — because `compute_confidence` returns a hard `0.0` whenever the model's own `insufficient_context` flag fires (no claims generated at all), and on this calibration set the model's raw insufficient-context detection caught 23/23 unanswerable items with no false negatives. Every item that got *any* non-zero confidence (9 items: a mix of adversarial-labeled-answerable and real single/multi-hop items) was, in this data, genuinely not-unanswerable — so a threshold of essentially "greater than exactly zero" already achieves 100% answered-precision on this set, and the sweep (in steps of 0.01) picks the first candidate above that floor.
**What this means, disclosed rather than smoothed over:** the confidence *score*'s continuous range (built from claim support, retrieval strength, and citation-sufficiency) isn't doing the decisive work here — the binary insufficient-context signal is. That's not necessarily wrong (a model that reliably self-reports "I don't know" is a good sign for a trust layer), but it means this particular calibration run mostly re-derives "trust the raw abstention signal, plus a hair of margin" rather than establishing a nuanced coverage/precision tradeoff curve. A future calibration set with more *borderline* answerable-but-weakly-grounded items (rather than this set's current split of "cleanly unanswerable" vs. "cleanly answerable") would exercise the continuous part of the formula more and likely produce a less degenerate threshold.
**Left as the live value rather than overridden**: 0.01 is what the calibration job is *supposed* to produce given its literal SPEC.md §8.5 procedure (sweep, pick the lowest threshold meeting the precision floor) — overriding it back toward the old 0.55 "init" default would be silently second-guessing the job's own output rather than trusting the measurement. `config.py`'s static `ABSTAIN_THRESHOLD=0.55` stays as the pre-calibration bootstrap value (SPEC.md literally frames it as "init"); the DB-backed live value (`app_settings`) is now the calibrated 0.01, exactly as designed.

**Also found live, unrelated to calibration correctness:** Docker Desktop itself crashed partway through this session (the Windows service backing it exited; `docker version` failed with a named-pipe error, `Get-Process` showed no docker-related process at all) — almost certainly sustained memory pressure from running the BGE embedder, MiniLM reranker, MiniCheck RoBERTa-Large, and Ollama's 4B model simultaneously for hours on the 8GB profile. The calibration script itself had already finished and returned exit 0 (its last action was `db.commit()`) before the crash, and Postgres's named volume survived the Docker Desktop restart intact (`calibration_runs`/`app_settings` both confirmed present afterward) — but this is a real operational ceiling of the local 8GB CPU-only profile worth knowing about, not just a one-off fluke.

## 2026-08-04 — Two more real bugs, both found running the actual Phase 4 baseline eval with Gemini generation

**Bug 1: Gemini's free-tier per-minute quota, with no retry, killed 27 of 39 full-pipeline items.** `GeminiProvider.generate()` fired one request per item with zero throttling; once Gemini's RPM cap was exceeded (after ~10 fast back-to-back calls, unlike Ollama's naturally-throttling multi-minute latency), every subsequent call 429'd and `run_item`'s per-item isolation correctly caught and logged each one — but 27 real failures meant most of the intended full-pipeline metrics were simply missing. **Fix:** `GeminiProvider._post_with_retry()` — exponential backoff (5s/10s/20s/40s, or the server's `Retry-After` header when present) on 429/503, up to 4 retries before surfacing a real error. This is a provider-level fix (any caller benefits), not an eval-runner-only patch.
**Bug 2, more serious — found only because bug 1 produced real failures for the first time**: once several `run_item()` calls failed and `execute_eval_run`'s per-item `except: await db.rollback()` fired (the same per-item isolation from DECISIONS.md 2026-08-02), the rollback expired *every* SQLAlchemy object already loaded in the session — including the `EvalResult` ORM objects from **earlier, already-successful** iterations, still sitting in the in-memory `results` list. When `aggregate_metrics()` later did a plain synchronous `for result in results: result.metrics.items()`, accessing `.metrics` on an expired object triggered SQLAlchemy's async-aware lazy-refresh machinery — which requires an active greenlet/await context that a bare `for` loop in a sync function doesn't have, raising `sqlalchemy.exc.MissingGreenlet`. That exception happened *after* the per-item loop, with no surrounding try/except, so it propagated all the way up and killed the Celery task — leaving the `EvalRun` row permanently stuck at `status="running"` with `finished_at=NULL`, indistinguishable from a run still legitimately in progress via the API or DB alone.
**Fix:** stopped relying on `EvalResult` ORM object identity surviving to the aggregation step at all. `execute_eval_run` now captures `(question_id, metrics_dict)` as a plain tuple into a separate list at the moment each item succeeds (before anything later in the run could roll back and expire it), and `aggregate_metrics()` takes that plain-data list instead of `list[EvalResult]`. No dependency on session/expiry state survives past the point of capture.
**Why this had never surfaced in three prior eval runs (Phase 3's two baseline attempts plus the successful one)**: every one of those runs happened to have zero per-item failures once the ReadTimeout fix landed, so `db.rollback()` was simply never called mid-run, so no object was ever expired mid-loop. The bug was latent in the aggregation code the whole time — it just needed a run with real, non-terminal per-item failures (which Gemini's rate limit finally provided) to be reachable at all.
**Recovery**: the stuck run (`phase4-trust-baseline-v1`) was manually finalized to `status="failed"` with an explanatory error (its 90 successfully-completed `eval_results` rows are still there, just under a run whose aggregate metrics were never computed) rather than left silently "running" forever; re-ran clean as `phase4-trust-baseline-v2` with both fixes in place.
**Reason this matters:** per-item isolation (2026-08-02) was built specifically so failures wouldn't be catastrophic — and it worked, right up until the *aggregation* step turned out to have its own, unrelated fragility against the very failure pattern isolation was designed to tolerate. Defensive code for a failure mode still needs to be exercised by a real failure to know if it actually works end-to-end, not just at the point it was written for.

## 2026-08-06 — Phase 5: the span exporter needs its own *synchronous* engine, and A/B comparison should be paired

**Span persistence runs on a second, sync SQLAlchemy engine — deliberately, not accidentally.** OTel's `SpanExporter.export()` is a synchronous method that `BatchSpanProcessor` calls from its own background thread. The app's engine is asyncpg. Reaching into an async engine from a non-async thread is exactly the shape of the `MissingGreenlet` bug that stranded a Phase 4 eval run (DECISIONS.md 2026-08-04), so `app/observability/exporter.py` opens a small `create_engine(...+psycopg, pool_size=1)` instead of bridging into the async one. psycopg was already a dependency, so this costs nothing but a few idle connections, and it keeps the two execution models from ever touching. Export stays batched off the request thread, so a slow or failing span write cannot add latency to the query it describes — and a failed export is logged and dropped rather than retried forever, because telemetry must never take down the path it observes.
**Two robustness details worth naming:** the exporter drops (rather than stores) a span with no `SpanContext`, since an orphan row can't be correlated to a trace and correlation is the entire point of persisting it; and the engine/session are created lazily on first export, so merely importing the module in a unit test never opens a connection pool. `SPAN_EXPORT_ENABLED` is a config kill switch for exactly that reason.

**A/B comparison uses a *paired* bootstrap, not the unpaired one Phase 3 already had.** `bootstrap_delta_ci` (Phase 3) resamples each side independently, which is correct for genuinely unpaired runs but wasteful here: every experiment in this project compares two configs over *the same golden set*, so each question yields a matched pair. `paired_bootstrap_delta_ci` resamples questions and takes both configs' score on each, which cancels per-question difficulty instead of letting it inflate the interval — the same true difference therefore reaches significance on far fewer items. There's a unit test asserting exactly that property (`test_paired_bootstrap_beats_unpaired_on_correlated_data`), not just that the function runs. The unpaired version stays for the genuinely-unpaired case rather than being replaced.
**`significant` is defined as "the 95% CI on the delta excludes 0"** — SPEC.md §3.5's promotion-gate rule, implemented once in the bootstrap helper so the Experiments page and (in Phase 6) the model-promotion gate cannot drift apart. A separate `improved` flag folds in direction, since `unsupported_claim_rate` and `latency_ms` are metrics where *lower* is the win; without that, a significant drop in unsupported-claim-rate would render as a regression.
**Comparisons only use questions present in both runs.** Phase 4's per-item failure isolation means a run can legitimately have holes (the OpenRouter daily cap left 7), and silently averaging over a different question set per side would bias the delta toward whichever run happened to complete the easier items.

**Two smaller calls, both deliberate:**
- **Nearest-rank percentiles, not interpolated.** A p95 that equals an actually-observed request can be clicked through to a real trace; an interpolated one describes a request that never happened. For a latency dashboard whose whole job is "which query was slow," the former is more useful.
- **Analytics aggregates in Python, not SQL.** At this project's volume (hundreds to low thousands of spans per window) the query cost is irrelevant, and keeping percentile logic in one unit-tested helper beats splitting it between a `percentile_cont` call and a Python path that could disagree.

**One bug caught in my own code before it shipped:** the first draft of the online monitor called the judge with `context=""`. Faithfulness is by definition a score *against* a context — that would have produced a confident-looking time series measuring nothing. Fixed to reconstruct the real context from the chunk ids in `claims[].citations` (the only stored record of what the model actually saw), and to skip an answer entirely when no context can be rebuilt rather than record a meaningless `0.0` that would drag the series down.

**Dev-environment gotcha, learned the expensive way:** the compose `api` service runs `uvicorn --reload` against the bind-mounted `./backend:/app`. Writing *any* file under `backend/` — including a new unit-test file that the running server never imports — triggers a reloader restart that kills every in-flight request. A ~10-minute live query and a queued API call were both lost to this mid-verification. Files at the repo root (`DECISIONS.md`, `document/`, `.env`) are outside the mount and safe to edit at any time; anything under `backend/` is not, while a long request is running. Worth knowing generally: `--reload` is watching the *filesystem*, not the import graph, so "this file isn't imported by the server" is no protection.

**Config change, not a code fix:** `GEN_TIMEOUT_SECONDS` raised 600 → 1200. Phase 4 measured real single-query generation at 339s and 619s on this hardware, so the old 600s ceiling was genuinely too tight for the live `/query` path and produced a `ReadTimeout` 500 on a query that was working correctly, just slowly. The eval runner already passed its own 1200s override (2026-08-02); this brings the interactive default in line with what the hardware actually does rather than leaving a known-failing default in place.

## 2026-08-06 — Phase 6: the promotion gate refused a real candidate, and that is the result

**Not adjusted to make it pass.** 47 training pairs is tiny and the baseline already scores 0.958 NDCG@10 on held-out, so there was almost no headroom; that was foreseeable before running it and the setup was left alone anyway. Tuning until the gate went green would have inverted the entire point of building a gate. The positive path is covered by a unit test (`test_promotion_accepts_a_real_significant_improvement`) rather than by manufacturing a "better" model, which would have proven nothing.

**Train/test contamination, caught in my own plan before it produced a fake number.** The first mining pass drew pairs from all 84 answerable golden-set items — the exact items the A/B gate scores. Training and evaluating on the same questions makes any measured "improvement" a memorization score, and would have left the gate rigorous in form and worthless in substance. Fixed with `scripts/split_golden_set.py`: a **hash-based** 66/51 split asserting zero overlap, with the 84 contaminated pairs **deleted rather than reused**. Split by `id` hash and not a seeded shuffle deliberately — a shuffle depends on input ordering, so a re-mine could silently move an item across the boundary and leak it.
**Consequence worth naming:** evaluating a candidate before promoting it required threading `reranker_path` through `retrieve()` → eval runner → Celery task → `POST /api/eval/run`. Without that, the only way to A/B a model would be to ship it first — i.e. the gate would depend on the decision it exists to make.

**Design calls that make the gate real rather than decorative:**
- **No override flag on the promote endpoint.** A promotion that can be forced by passing a parameter is not a gate. A refusal returns **200 with the reason and the per-metric CI table**, because the gate correctly declining a weak candidate is a successful answer to the question asked, not a failed request.
- **Gate metrics are retrieval-only** (`ndcg@10`, `hit_rate`). A reranker can only affect faithfulness *through* retrieval, so including generation metrics would inject noise — and a dependency on whichever generation provider happened to run — into a retrieval decision.
- **Fine-tuning registers `candidate`, never `active`.** Training and shipping are separate operations by construction, so a training run cannot quietly become production.
- **"One active model per kind" is a partial unique index in Postgres**, not just application logic — verified by confirming the DB rejects a second active insert. Application-only invariants fail open when a code path is missed.
- **A bare thumbs-down does not become a training pair.** It identifies wrong chunks but not the right one, so it yields negatives with no positive and cannot form a triple. Only corrections (which name the true answer) produce pairs; bare downvotes feed failure clustering, where an unlabelled negative genuinely belongs. Inventing a positive is how a feedback loop teaches itself nonsense.
- **Re-mining deletes prior mined pairs.** Hard negatives are defined relative to the *current* ranker; keeping stale ones trains the next model against confusions its predecessor already fixed.

**Local fine-tuning was justified by measurement, not assumption.** Before committing to the approach, benchmarked the actual targets on this hardware: bge-small is 33M params (~534MB train footprint), MiniLM 23M (~363MB) — a different class entirely from the *inference* models whose concurrent residency crashed Docker twice (Ollama 4B ~2.5GB + MiniCheck 1.4GB). Measured throughput at batch 16/32/64: **batch 32 is the sweet spot** (29.7 pairs/s, 1.48GB peak); batch 64 doubles memory and gets *slower*, past the CPU's efficient working set. The real 129.5s training run matched the projection. No cloud GPU needed.

**Third dev-environment reload gotcha, distinct from Phase 5's.** The first fine-tune request was rejected with `KeyError: 'finetune_reranker'`: the API (`uvicorn --reload`) had picked up the new task module immediately, but the Celery worker — which runs no reloader — had never registered the new tasks and silently rejected the message. Phase 5's lesson was that `--reload` is too aggressive (it kills in-flight requests on any file write); this one is the mirror image, that the worker doesn't reload at all and needs an explicit restart after adding tasks.

## 2026-08-06 — Measuring the untested targets: a real confidence bug, and a p95 I had reported wrongly

**Measured the two SPEC.md §7.2 targets that had never been computed** (ECE; and latency, properly this time). Red-team ASR remains genuinely unmeasured because the harness is Phase 7 work — that is a build gap, not a measurement gap, and is not counted as "tested" here.

**ECE = 0.234 against a ≤0.10 target — FAIL, and the direction is informative.** Mean confidence 0.599 vs actual accuracy 0.833: the system is systematically **under**-confident. Safer than the reverse, but still miscalibrated, and it costs real coverage by abstaining when it needn't. Implemented `app/trust/ece.py` (ECE + MCE + reliability bins) with the scope decision written into the module: ECE is computed over **answered** items only, because `compute_confidence` returns a hard 0.0 on insufficient context, so a correctly-abstained item would enter the lowest bin as a "correct" outcome and make calibration look worst exactly when the trust layer is working. Abstentions are declines to predict, and are already scored by `abstention_recall_unanswerable` / `answered_precision`.

**Root-caused it to a bug in my own Phase 4 confidence formula.** `retrieval_strength` averaged `sigmoid(rerank_score)` across *all* retrieved chunks. Concretely, item `si_063`: the correct document was retrieved at rank 1 (score +4.6 → sigmoid 0.990) and the cross-encoder correctly rejected the tail (−2.8 to −7.3) — average **0.136**. The formula *punished the reranker for being decisive*: a mushy ranker scoring everything ~+1 would have scored ~0.7. Sharper discrimination produced lower confidence, which is backwards. Fixed to average only the top-`CONFIDENCE_RETRIEVAL_TOP_K` (=2) scores. Component gap vs accuracy: **−0.225 → −0.044**; overall **ECE 0.222 → 0.176**.
**Top-2 rather than top-1 on reasoning, not on the decimal**: top-1 measured 0.184 and top-2 0.176, which at n=25 is not a distinguishable difference; top-2 was chosen because it requires corroboration instead of trusting one lucky chunk.
**Still short of 0.10, and small-sample noise is not the excuse.** Bootstrap 95% CI on the fixed ECE is **[0.133, 0.301]** — the target lies outside it. The residual is isolated and named: MiniCheck's `claim_support` averages **0.655 against 0.880 accuracy (+0.225 gap)**, because it is a strict sentence-level entailment model that under-scores paraphrase and cross-chunk aggregation. Closing that properly means fitting a calibration map (Platt/isotonic) on held-out judged data — which needs roughly 90 more judged items (~7.7h of local generation+verification, or several times the free-tier API day caps). Recorded as the next concrete step rather than papered over.

**I had reported the p95 latency wrongly, and am correcting it.** Phase 5 quoted "p50/p95/p99 = 264,880 ms" straight from the analytics endpoint. That window contained **exactly one query**, which was also that process's first — so it included cold model loads. A percentile over n=1 is one sample, and quoting it as a p95 was sloppy. Direct measurement: **warm `retrieve()` p50 = 8.2s vs 25.8s cold**, and inside it **dense+sparse search is only 22.8 ms**. Two things had made retrieval look slow that aren't: the RETRIEVER span *nests* the RERANKER span (so the two must never be added), and the traced query paid one-time model loading. Retrieval on 1,895 chunks is genuinely fast; the cross-encoder is essentially all of its cost.

**Found a real 2.6x retrieval optimization and deliberately did not ship it.** Capping `RERANKER_MAX_LENGTH` 512 → 256 measured (50 candidates, CPU): 6.4s → 1.9s. A/B'd it on the 51-item held-out split through the Phase 5 experiment machinery rather than eyeballing: **latency −5022ms, CI [−5376, −4680], significant**; NDCG@10 −0.0216 and MRR −0.0293 with CIs straddling zero. "Not significant" is not "no effect" — both point estimates are negative and the NDCG CI reaches −0.068, past SPEC.md §7.2's −0.03 regression tolerance. Decisive argument for leaving it at 512: on this profile the 5s saved is **~2% of a ~250s query** dominated by generation and claim verification, so it buys nothing against the 3.0s p95 target while carrying unquantified quality risk. Kept as a documented config lever for Phase 8, where hosted generation makes retrieval the dominant term and the trade actually pays.

**p95 ≤ 3.0s is not reachable on this hardware, and that is a hardware verdict, not a tuning one.** Warm end-to-end is ~250s: generation ~158s (4B model, CPU) + MiniCheck verification ~86s + retrieval ~8s. Even driving retrieval to zero leaves ~244s. Hitting 3.0s requires hosted generation (measured at 1.5–2.8s) *and* GPU/hosted claim verification — i.e. a different deployment profile. SPEC.md §7.2 already scopes this metric to "report; gate in load test only", which lands in Phase 8.

## 2026-11-15 — Sparse search required every query term; replaced with BM25 computed in SQL

**Found by measuring the sparse leg on its own**, which the golden set had never done (dense search plus the reranker carry it to hit_rate 0.988 regardless). `sparse_search` built its query with `websearch_to_tsquery`, which ANDs every term. A natural-language question almost never has all of its words in one chunk: on 50 public MS MARCO questions against a 5,043-passage corpus, 12 returned no rows at all and 45 returned fewer than the 10 asked for. The sparse half of "hybrid" retrieval was contributing close to nothing.

**OR matching alone was not the fix.** Rewriting the query to match any term (keeping `ts_rank_cd`) filled the candidate list but ranked it badly, because `ts_rank_cd` has no inverse document frequency: a chunk that repeats common words outranks one containing the rare word the question is about. Fused with dense results, that made hybrid retrieval worse than before on three of the four corpora tried. Dropped.

**Decision:** Okapi BM25 (k1 = 1.2, b = 0.75, non-negative idf) computed in one SQL statement over the existing `tsv` column: term frequency from a lexeme's position count, document length from `token_count`, candidates from the GIN index. No new dependency, no second index to keep in sync with the table, no Postgres extension.

**A planner trap on the way:** the first version took up to 1.7 s per query. `EXPLAIN ANALYZE` showed Postgres had inlined the term-statistics CTE and was re-running the document-frequency count once per matched row (1,726 times for one query). `AS MATERIALIZED` on both CTEs took that query from 2,010 ms to 56 ms. Measured p50 is 20-60 ms on 3-5k chunks and 0.2-0.3 s for long questions on 8k chunks. idf and average length are recomputed per query, so this is sized for thousands of chunks, not millions; the module names the ceiling and the upgrade path.

**Check left behind:** `tests/integration/test_sparse_bm25.py` runs the real SQL against Postgres (now a step in `evals.yml`): a question containing a word no chunk has must still return matches, ordered by rarity and frequency. The old query returns nothing for it.

**Reason this matters:** a component that is never measured alone can be dead for months behind a strong neighbour.

**Update, 2026-11-16:** measured end to end the next day, fusing BM25 into the final ranking made it *worse* on two public benchmarks and changed nothing on the golden set, so keyword search is now off by default. BM25 stays as the implementation for when it is switched on. See the 2026-11-16 entries.

## 2026-11-16 — Public benchmarks through the project's own eval runner

**Why:** the golden set was written and judged by the project's own 4B model and already scores hit_rate 0.988, so it cannot show a retrieval change. Two public BEIR collections with published numbers were added: **SciDocs** (25,657 papers, 1,000 test questions; relevant = papers the question's paper cites) and **ArguAna** (8,674 arguments, 1,406 test questions; relevant = the counter-argument).

**How:** `backend/scripts/beir.py` downloads each collection from the BEIR distribution and loads it into its own database (`ragforge_beir_<name>`, never the demo corpus), one embedded chunk per document. The test questions are written in the project's own golden-set format, and runs go through `app.evals.runner.execute_eval_run`, the same code as `POST /api/eval/run`, so runs appear on the Golden set and A/B pages. The runner gained what public benchmarks need:
- graded NDCG@10 over all relevant documents, as trec_eval computes it (the project's own `ndcg@10` credits only the first hit), and recall@10;
- the same score after each stage (dense, fused, final), plus each question's whole candidate pool with its dense rank, BM25 rank, RRF and rerank scores. `beir.py analyze` replays pools under other ordering policies offline, in seconds;
- ArguAna's questions are themselves documents of the collection; like BEIR's own scoring, a question's own document is skipped.

Policies are chosen on a fixed 30% of each collection's questions (hash of the id), and the other 70% is reported alongside. The same commands run on the project's golden set over its main database (`beir.py run golden`), so every change is also checked on the real use case. The runs used the GPU profile; scores do not depend on the device, timings do.

## 2026-11-16 — The reranker abstains below a confidence threshold; keyword search off by default

**What the stage scores showed** (NDCG@10, dev / test split, keyword search on, full candidate union reranked):

| | SciDocs | ArguAna |
|---|---|---|
| dense alone | 0.221 / 0.198 | 0.598 / 0.606 |
| dense + BM25, RRF | 0.209 / 0.182 | 0.551 / 0.555 |
| reranked (production) | 0.183 / 0.163 | 0.426 / 0.414 |

Dense retrieval alone reproduces the embedding model's published scores (bge-small-en-v1.5: SciDocs 0.205, ArguAna 0.596). Every later stage lost ground. The MS MARCO MiniLM cross-encoder alone cost 0.17 on ArguAna; the BEIR paper reports the same model failing on ArguAna, a task "extremely different to the MS MARCO training dataset".

**Decision:** keep the reranker but let it abstain. Candidates it scores at or above `RERANK_LIFT_THRESHOLD` move up in its order; it leaves every other candidate in retrieval order (`app.retrieval.pipeline.apply_rerank`). This is the trust layer's rule, withhold what you are not sure of, applied to ranking. A threshold sweep over SciDocs dev, ArguAna dev and the whole golden set (gain over dense alone):

| Threshold | SciDocs dev | ArguAna dev | Golden (84) | Sum |
|---|---|---|---|---|
| none (full reranking) | -0.038 | -0.172 | +0.014 | -0.196 |
| 3.5 | -0.007 | -0.005 | +0.019 | +0.007 |
| **4.0** | -0.004 | -0.003 | **+0.020** | **+0.013** |
| 4.5 | -0.004 | -0.002 | +0.017 | +0.011 |
| 6.0 (rarely lifts) | -0.001 | +0.001 | 0.000 | -0.001 |

4.0 keeps the reranker's gain on the project's own questions and gives back almost nothing on the out-of-domain sets. The golden set's 84 questions were used in choosing, so it serves as a guard here, not an unbiased test.

**Keyword search off by default (`SPARSE_TOP_K=0`):** with the full reranker, fusing BM25 lowered NDCG@10 on SciDocs (-0.010, interval [-0.014, -0.007]) and on ArguAna (-0.004 [-0.007, -0.001]), and the fused stage is below dense alone on both. On the golden set it changed nothing, and its SQL adds 0.3-0.9 s per question. The old all-terms query had contributed nothing either: on the golden set, removing it gave identical results on every question, and on SciDocs it returned no rows for 890 of 1,000 questions. "Hybrid" retrieval had been dense-only in practice. BM25 remains the implementation when `SPARSE_TOP_K > 0`.

**Tried and dropped:** pseudo-relevance feedback (move the query embedding toward its top-k results and search again, `DENSE_FEEDBACK_DOCS`). The best setting on the combined dev split (3 results, weight 0.25) gained 0.004 on SciDocs test and lost 0.004 on ArguAna test, so it is left available and off. Reranking the whole candidate union instead of the fused top 50 did not rescue BM25 either.

**Result, final configuration through the production pipeline, full test splits:**

| | Before | After | Difference [95% interval] |
|---|---|---|---|
| ArguAna NDCG@10 | 0.432 | 0.599 | +0.167 [+0.148, +0.185] |
| SciDocs NDCG@10 | 0.182 | 0.201 | +0.019 [+0.011, +0.026] |
| Golden set NDCG@10 (first hit) | 0.948 | 0.938 | -0.011 [-0.036, +0.012] |

On the 70% held-out split: ArguAna 0.600, SciDocs 0.193. Both beat every system in the BEIR paper (best: ArguAna 0.493, SciDocs 0.166) and match the embedding model's published scores (0.596, 0.205). They do not exceed them, and no claim of doing so is made. The golden set shows no significant change; its point estimate is slightly lower, and one question's paper fell out of the top 8.

**Abstain threshold recalibrated after the change.** The trust layer's threshold had been calibrated in August with full reranking, and confidence reads the top two rerank scores among the passages used. `scripts/calibrate_abstain_threshold.py` was rerun on the 40-item calibration set with the new defaults, generating with qwen3:4b-instruct. It chose **0.010**, the August value:
- all 23 unanswerable items scored exactly 0, from the model's own insufficient-context flag;
- the 9 items that scored above 0 are all answerable, so answered-precision is 1.00 with 23/23 correct abstentions;
- coverage is 9 of 40. One answerable single-hop question (si_042) and 7 of the 10 adversarial items also scored 0 and are withheld. That is the trust layer's coverage cost, not a precision failure.

As in August (2026-08-03), the continuous part of the confidence score decides nothing on this set. The live value is stored in `app_settings`, and the run with its curve in `calibration_runs`.

## 2026-11-16 — The claim checker is strict, measured on SciFact

`backend/scripts/scifact_checker.py` scores every (claim, abstract) pair of SciFact's labelled dev split (Wadden et al., 2020; 323 pairs) with the production MiniCheck provider and threshold (0.5). A "supported" verdict is right only for pairs experts labelled SUPPORT.

| | Judged supported |
|---|---|
| SUPPORT (138) | 55.8% [47.1, 64.5] |
| CONTRADICT (71) | 4.2% [0.0, 9.9] |
| NOT_ENOUGH_INFO (114) | 0.9% [0.0, 2.6] |

Precision of a "supported" verdict 95.1% [90.1, 98.8], balanced accuracy 0.768 [0.724, 0.810], AUROC 0.904 [0.868, 0.936]. The checker almost never passes a claim it should not, but it rejects 44% of claims that are supported. This is the measured cause of the 0.398 unsupported-claim rate (2026-08-06) and of the trust layer's under-confidence (ECE). Per-pair results (ids and probabilities, no SciFact text) are in `eval-datasets/benchmarks/scifact-checker-dev.json`.

**The threshold is not the lever.** The scores rank well (AUROC 0.90), so a lower threshold looked like a free way to pass more supported claims. `scifact_checker.py threshold` chose it on SciFact's train split alone (894 pairs), by the rule the checker exists for: the highest balanced accuracy whose "supported" verdicts stay right at least 90% of the time. The rule picked 0.5, the value already in use; at 0.46 train precision is 0.897, already under the floor. So dev is unchanged. What a lower threshold would buy, on train:

| Threshold | Supported claims passed | Precision of "supported" | Balanced accuracy |
|---|---|---|---|
| 0.5 (current) | 53.8% | 90.0% | 0.748 |
| 0.4 | 60.5% | 88.9% | 0.776 |
| 0.3 | 66.8% | 86.7% | 0.798 |
| 0.1 | 78.9% | 77.2% | 0.813 |

Balanced accuracy keeps rising as the threshold drops, but only by letting more contradicted and unsupported claims through, which is the failure the checker is there to prevent. The threshold stays at 0.5. Passing more supported claims needs a stronger checker model, or more context around the cited chunk, not a looser threshold. Sweep and both summaries: `eval-datasets/benchmarks/scifact-checker-threshold.json`.

## 2026-11-16 — Ingestion and reproducibility fixes found while rebuilding the corpus

- **The golden set's corpus could not be rebuilt.** `seed_demo_corpus.py` asks arXiv for today's best matches, and those drift, so a fresh clone got different papers from the ones the golden set's expected ids point at. `--from-golden-set` now fetches exactly the 37 paper versions it references. The rebuilt corpus reproduces the August baseline closely (hit_rate 0.976 against 0.988, NDCG@10 0.948 against 0.950).
- **NUL characters failed whole documents.** Two of the 37 papers extract to text containing 0x00, which Postgres rejects in a text column, and the whole document failed at insert time. `parse_document` now strips it, at the one point every ingestion path goes through.
- **Docling failed on every document under the GPU profile.** Docling runs in a child process so it can be killed on timeout. Forked from a worker that had already initialised CUDA for the embedder, the child could not use CUDA, so every document silently fell back to pypdf. The child is now spawned instead, and spawned processes need the project on their path: the image now sets `PYTHONPATH=/app`, which also retires the `-e PYTHONPATH=/app` workaround in older commands. Each spawned parse reloads Docling's models (about 5 minutes per paper here), so the corpus used for these measurements was left parsed by pypdf; both sides of every golden-set comparison used the same corpus.
