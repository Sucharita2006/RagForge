# Resume bullets — ragforge

Running log of quantified, ATS-keyword-rich bullets, updated at each phase close with real measured numbers (never invented ones). Draft phrasing now; tighten wording once the full project is done and a target job description is known.

## Project-level (draft — revisit after Phase 8 with final numbers)

- Built **ragforge**, a self-hosted Retrieval-Augmented Generation (RAG) platform with hybrid retrieval (dense + sparse + RRF fusion + cross-encoder reranking), per-claim citation verification, calibrated abstention, a CI-gated evaluation harness, an automated model fine-tuning/promotion flywheel, and a prompt-injection red-team suite — deployed via Docker Compose (local) and Cloud Run (public demo).
- Designed and measured a **pgvector filtering/latency architecture** (iterative-scan HNSW, partial indexes, `halfvec` quantization) via a controlled multi-configuration benchmark sweep, reproducing a documented pgvector failure mode and measuring the fix, rather than assuming vendor-claimed numbers. *(Numbers land at Phase 8 close.)*

## Phase 0 — Scaffold (2026-07-30)

- Stood up a production-shaped monorepo (FastAPI + Next.js/TypeScript + PostgreSQL/pgvector + Redis + Celery) with Docker Compose orchestration, Alembic migrations, and a GitHub Actions CI pipeline (lint, type-check, unit tests) passing from the first commit — establishing a verifiable, incremental build history rather than a single monolithic upload.

## Phase 1 — MVP vertical slice (2026-07-31)

- Built an end-to-end self-hosted RAG pipeline — Docling document parsing, `bge-small-en-v1.5` embeddings, PostgreSQL/pgvector (HNSW) dense retrieval, and a locally-hosted Qwen3-4B model (via Ollama) for grounded generation — and measured a **dense-only retrieval baseline of hit_rate@10 = 1.0, MRR = 0.935, NDCG@10 = 0.951** on a 40-document, 1,492-chunk corpus, establishing `baseline-v0` for every later retrieval improvement to be measured against.
- Designed a citation pipeline that parses per-claim source citations from free-text generation (rather than trusting constrained JSON-schema decoding, which measurably degraded a small local model's output quality) and filters out fabricated citation IDs against the real retrieved chunk set — a cheap integrity check ahead of full NLI-based claim verification.
- Diagnosed and fixed a citation-parsing bug via unit tests (not manual testing) that silently dropped valid citations under a specific sentence-boundary pattern, and a Celery/asyncio bug (per-task event loops vs. a shared connection pool) causing intermittent ingestion failures — both caught and resolved by building a real automated test suite and running the full pipeline against production-realistic data, not just inspecting the code.
- Automated demo-corpus construction by querying arXiv's API directly for real, current papers (rather than a hardcoded list), ingesting 40 LLM/RAG papers (707 pages) end-to-end with zero manual intervention.

## Phase 2 — Full retrieval engine (2026-08-01)

- Built a hybrid retrieval pipeline — Postgres full-text search fused with dense HNSW search via Reciprocal Rank Fusion, then cross-encoder reranking (MiniLM) — and measured a **+3.2 point NDCG@10 gain (0.951 → 0.982) and +4.0 point MRR gain (0.935 → 0.975) over the Phase 1 dense-only baseline**, with hit_rate@10 holding at a perfect 1.0, on the same 40-document corpus.
- Reproduced pgvector's documented filtered-search failure mode on real production data — not a synthetic benchmark — by using `EXPLAIN ANALYZE` to diagnose why the bug didn't initially appear (Postgres's own planner sidesteps the approximate HNSW index in favor of an exact scan below a size threshold), then forcing the approximate index path to demonstrate the bug (**0 of 10 requested rows returned** under `hnsw.iterative_scan=off`) and its fix (**10/10 reliably** under `relaxed_order`, at a measured ~3-4x but sub-10ms latency cost).
- Diagnosed and fixed a CPU-resource leak invisible to the task queue itself: a timeout guard around an unbounded third-party OCR call used a thread (unkillable in Python), which left runaway work consuming ~900% CPU indefinitely after the task it belonged to had already "succeeded" and moved on. Replaced it with a real child-process-based timeout that the OS can forcibly terminate, verified live via a CPU drop from ~800% to near-zero at the exact moment the fix took effect.
- Implemented parent-child hierarchical chunking (precise retrieval on child chunks, full context via parent expansion), session-aware conversational query rewriting, and a Redis-backed semantic cache with corpus-version invalidation (a cached answer can never outlive the source data it was computed against) — each verified against the live API, not just unit-tested in isolation.

## Phase 3 — Eval harness + CI gates (2026-08-02)

- Built a CI-gated evaluation harness — a curated 117-item golden set (single-hop/multi-hop/unanswerable/adversarial), retrieval + generation + LLM-as-judge metrics with bootstrap 95% confidence intervals, and a persisted eval-run history queryable from a dedicated Evaluations UI — turning ad-hoc mini-eval scripts into a real, repeatable regression signal a PR can automatically fail against.
- Measured a full-pipeline baseline on real hardware (not a toy sample): **hit_rate 0.988, MRR 0.939, NDCG@10 0.950** (95% CI, n=84 answerable items) against the Phase 2 hybrid+rerank pipeline, plus abstention behavior exceeding target (**answered-precision 1.00, unanswerable-recall 1.00**, n=39 stratified subset) — all measured via bootstrap resampling rather than reported as raw point estimates.
- Designed a single combined pointwise-rubric LLM-judge prompt (faithfulness/answer_correctness/context_precision/context_recall scored in one call instead of four) as a deliberate latency optimization for CPU-bound local inference, with Redis-backed result caching keyed by dataset version and judge model.
- Faced a live $0-budget-vs-quality tradeoff explicitly rather than silently defaulting: chose to keep golden-set generation and LLM-judging fully self-hosted on a local 4B model instead of adding a cloud API key, then measured and disclosed the real cost of that choice (judge-scored faithfulness/context_recall/answer_correctness landed below spec target, exactly as predicted, while every judge-independent metric met or exceeded target) — the provider is dependency-injected, so upgrading later needs no harness changes.
- Found and fixed a fragile-harness design flaw under real load: a single slow item's timeout was aborting an entire multi-hour, ~100-item batch run and discarding already-computed results. Fixed with per-item failure isolation (one bad item is logged and skipped, not fatal to the run) plus a background-appropriate timeout budget — a general robustness pattern, not a one-off patch.
- Shipped an automated CI regression gate (`evals.yml`): a synthetic fixture corpus is ingested fresh and queried end-to-end on every PR, hard-failing the build if a real retrieval regression is introduced — verified live by running the full gate against the working stack before merging.

## Phase 4 — Trust layer (2026-08-05)

- Built a claim-level verification and calibrated-abstention layer on top of the RAG pipeline: every generated sentence is checked against its cited source spans by an NLI entailment model (MiniCheck RoBERTa-Large, self-hosted CPU), scored into a weighted confidence value, and gated against a threshold fit on a held-out calibration split — so the system declines to answer rather than emitting weakly-grounded claims.
- Fit the abstention threshold empirically instead of hand-tuning it: swept 101 candidate thresholds against a 40-item calibration set, measured the coverage↔answered-precision curve at each, and persisted both the chosen value and the full curve for a live Settings slider. Measured **answered-precision 1.00 and unanswerable-recall 1.00** (23/23 unanswerable items correctly abstained).
- Verified the trust layer added **zero retrieval regression** by re-measuring against the prior phase's baseline on identical corpus and pipeline (hit_rate 0.988→0.988, NDCG@10 0.950→0.949, MRR 0.939→0.936, all within bootstrap CI noise) — the kind of check that distinguishes "shipped a feature" from "shipped a feature without breaking anything."
- Reported a **missed target honestly rather than tuning the metric to pass**: unsupported-claim-rate measured 0.398 against a ≤0.05 goal, root-caused to strict sentence-level entailment semantics plus an untuned generator, and documented as deferred generation work instead of adjusting the threshold or quietly dropping the metric.
- Diagnosed a latent data-integrity bug that only became reachable under real failure conditions: per-item error isolation triggered SQLAlchemy session rollbacks that silently expired already-loaded ORM objects from earlier successful iterations, causing the aggregation step to crash (`MissingGreenlet`) and strand the job in a permanent "running" state. Fixed by capturing results as plain data at the point of success, eliminating the dependency on session lifetime entirely.
- Worked around a hard infrastructure ceiling under real constraints: local memory pressure (4 concurrent ML models on a 16GB machine) crashed the container runtime mid-run, so the eval harness's generation provider was made swappable per-run, then routed through a hosted free-tier API — cutting a multi-hour run to ~1 hour without changing production behavior, and adding retry-with-exponential-backoff to both hosted providers along the way.

## Phase 5 — Observability + experiments (2026-08-06)

- Built end-to-end distributed tracing for the RAG pipeline: a custom OpenTelemetry span exporter persists every pipeline step (embedding, retrieval, reranking, generation, claim verification) to PostgreSQL with per-span latency, token counts, computed cost, and retrieved-document scores — surfaced as a clickable waterfall UI, turning "the query was slow" into "the reranker took 4.0s of the 17s."
- Designed the exporter around OpenTelemetry's synchronous, off-thread contract by giving it a dedicated sync database engine rather than bridging into the app's async one — avoiding a known async-context failure mode that had previously stranded a background job — and made telemetry strictly fail-open, so a failed span write can never add latency to or take down the request it describes.
- Shipped an A/B experiment harness that compares two pipeline configurations with **paired bootstrap 95% confidence intervals**, treating a metric as changed only when its CI excludes zero. Chose paired over independent resampling because both runs score the same evaluation set, which cancels per-question difficulty and reaches significance on materially fewer items — with a unit test asserting the paired interval is genuinely tighter, not merely that the code runs.
- Validated the harness on two real prior runs and it correctly separated signal from noise in one pass: flagged a **5x latency improvement** (−120s, CI [−158s, −83s]) and a **real context-precision regression** (−0.18, CI [−0.29, −0.08]) as significant, reported exactly zero change on retrieval metrics where the pipeline was genuinely identical, and declined to claim wins on three generation metrics whose intervals straddled zero.
- Built an analytics dashboard (p50/p95/p99 latency, cache-hit and abstention rates, cost per query, per-stage latency breakdown) and a nightly online-monitoring job that judge-scores sampled production answers for faithfulness and alerts on a 7-day drop.
- Caught a self-inflicted measurement bug before shipping: the monitoring job initially scored faithfulness against an empty context, which would have produced a confident-looking time series measuring nothing. Fixed to reconstruct each answer's true source context from its stored citations, and to skip unscorable answers rather than record a misleading zero.

## Phase 6 — Learning flywheel (2026-08-06)

- Built a closed-loop retrieval-improvement system: user feedback and hard-negative mining produce training pairs, a fine-tuning job trains a candidate cross-encoder reranker, and a **statistically gated A/B promotion** decides whether it ships — with the candidate hot-swappable via a database registry pointer rather than a redeploy.
- Implemented the promotion gate so it **cannot be bypassed**: no override flag, the endpoint computes the verdict itself, and a model is promoted only if a paired bootstrap 95% CI on ΔNDCG@10 or Δhit-rate **excludes zero** with no significant regression on the other. Ran it live against a real fine-tuned model and the gate **refused promotion** (ΔNDCG −0.022, CI [−0.059, +0.004]) — demonstrating the mechanism works rather than tuning the setup until it produced a green result.
- Caught train/test contamination in my own experiment design before it produced a meaningless number: training pairs were being mined from the same golden-set items the A/B gate scores, which would have measured memorization rather than generalization. Fixed with a deterministic hash-based train/held-out split (chosen over a seeded shuffle because shuffles depend on input ordering and can silently leak items across the boundary), and **deleted** the contaminated pairs rather than reusing them.
- Enforced the "exactly one active model per kind" invariant as a **partial unique index in PostgreSQL**, not only in application code, and verified it by confirming the database rejects a second active row — an application-only invariant fails open the moment a code path is missed.
- Made a deliberate data-quality call against the obvious shortcut: a bare thumbs-down identifies which chunks were wrong but not which was right, so it cannot form a valid training triple. Rather than synthesize a positive, only user corrections generate training pairs; unlabelled negatives feed failure clustering instead — because inventing ground truth is how a feedback loop teaches itself nonsense.
- Justified local CPU fine-tuning with a benchmark rather than an assumption: measured parameter counts, memory footprint, and throughput at three batch sizes, finding batch 32 optimal (29.7 pairs/s, 1.5GB peak) while batch 64 was both slower and heavier. The real training run (129.5s) matched the projection, avoiding an unnecessary cloud GPU dependency.
